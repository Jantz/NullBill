# CLAUDE.md

Guidance for Claude sessions working in this repository.

## What this is

NullBill turns a spare x86 machine running Proxmox VE into a self-hosted dev
server from one declarative config. `nullbill` runs on a controller the owner
names and reaches the host over SSH; it never runs on the host. Only `probe`,
`plan`, `apply` (stages so far: render, tailnet, host, tofu, release, router, proxy, updates, ca, postgres, monitoring, forgejo, inference, files, media, torrents, games, ci, agents, logs, backups, vpn, custom, verify),
`verify` and `upgrade` exist.

## Layout

- `src/nullbill/data/catalog.yaml`: platform defaults (zones, roles, services, engine table).
- `src/nullbill/data/schema.yaml`: JSON Schema for `config.yaml` and for the merged model.
- `src/nullbill/probe.py`: read-only probe commands and their parser.
- `src/nullbill/plan.py`: sizing rules; every rule failure is collected and reported together. Memory: VMs count in full, containers at `host.container_share_pct` (50) of their limit, since an LXC limit is not a reservation; `HostMemoryLow` alerts when that bet fails. A GPU's VRAM is needed only when inference budgets it; the page asks for it when the probe (no driver yet) cannot read it.
- `tests/fixtures/<class>.yaml`: synthetic probe output for small, mid, large.
- `tests/golden/<class>.plan.yaml`: expected plans. Regenerate with `UPDATE_GOLDEN=1 python3 -m pytest` and review the diff.
- `hooks/`, `tools/denylist-scan`: privacy hooks. `tools/install-hooks` enables them.
- `src/nullbill/flows.py`: the one flow list both firewall layers are generated from.
- `src/nullbill/firewall.py`: pve-firewall files (`host.fw` goes to `/etc/pve/local`, the rest to `/etc/pve/firewall`); `tools/check-firewall` parses and compiles them with the stock pve-firewall in a container and runs PVE's simulator (LAN to 8006/22 dropped only when closed; the closed `cluster.fw` sets `local_network` to the vpn guest, since PVE adds that alias to `management`).
- `src/nullbill/router.py`, `src/nullbill/proxy.py`: router (nftables, dnsmasq, interfaces) and Squid files; `tools/check-guests` checks them with Debian 13's nft, dnsmasq, ifupdown and squid.
- `src/nullbill/lan.py`: closing the LAN to 8006 and 22 (#9). `apply --close-lan` (host stage only) arms a 15-minute systemd-run timer on the host that restores `/root/nullbill/cluster-lan-open.fw` (and a marker that `nb-lan-revert-boot.service` acts on at boot, since the timer does not survive a restart), then installs the closed cluster.fw; `--confirm-lan` stops the timer and removes the marker, and the page runs it only for a request from the vpn guest's address. State in `$NULLBILL_HOME/lan.json`; while closing or closed the controller reaches the host at its mgmt address, verify checks the LAN address (DEGRADED while open), and once closed the page refuses clients outside the network base. The host's timer reopens the LAN without telling the controller, so a close past its deadline is settled with the host before anything says "closing" (`lan.overdue`, `lan.settle` asks `lan.ARMED`; the page's `App.lan_view` at most every 30 s, verify before its checks): open again, with `lapsed` (when it ran out) in `lan.json` for the page to say so; `lan_view` gives the page `left_s` to count down.
- `src/nullbill/tailnet.py`: Tailscale policy from people and roles, the only per-person gate; plan fails past the free-plan limits in `catalog.yaml`. A person's `services` become a grant from their login (no group: only a role that is held and named by a port gets one), and each person gets a policy test: accepted on what they hold, denied on the host, the router and every other person-facing port. `routes` are the zones the vpn guest advertises. Every group and every person may reach the router's access-zone leg (`tailnet.nameserver`) on 53, which the vpn guest advertises as a /32.
- People (docs/adr/0011-people.md, docs/runbooks/add-person.md): `src/nullbill/people.py` and the page's Access, People tab (`/api/people`, `/remove`, `/sync` in `web/server.py`). A port can be given to a person only if its `from` lists `shared` (never in mgmt); `shared` opens the firewall from the vpn guest like a role, whoever holds it, so a person more or less changes `tailnet/policy.json` only and needs no setup run. The page pushes to Tailscale first (`tailscale.sync_policy`: validate with tests, set with the ETag, read back) and writes `config.yaml` only after, keeping its mtime so no setup run is asked for; before the first setup run or without an OAuth client it only saves. Invitations to the tailnet cannot be made with an OAuth client, so the owner sends them from Tailscale's Users page and the page writes what to send the person (each service's `share` block in the catalog). Removing deletes the Tailscale user when the client holds `users`. verify: `Tailscale holds each person to the services picked for them` compares the live policy with the rendered one (SKIP without a client). The tick list says what a tick gives: `people.shareable` carries `opens` (the shared ports in words) and `access` (the catalog's `share.access`: what a person can do behind the port, which is the program's business; `people.UNKNOWN_ACCESS` for a service without one, and a test holds that every catalog service with a `shared` port has one), shown under a service once it is ticked. A refusal with several reasons (`errors.Refused`, Tailscale's failing tests from `TailscaleError.reasons`) reaches the page as `headline` and `errors` beside `error` (`server.refusal`), and the tab shows a headline with a list (`showProblem` in `app.js`), never one joined sentence.
- `src/nullbill/tailscale.py`: Tailscale's API with the owner's OAuth client (`tailscale_client_id`/`_secret` in secrets, pasted on the page). apply's tailnet stage, before the host stage, counts tagged devices, has Tailscale validate and test the rendered policy, pushes it with the read ETag and reads it back; any failure stops apply. The vpn stage runs only once that policy is in place. `NULLBILL_TAILSCALE_API` points it at a stand-in.
- `src/nullbill/names.py`: names such as `forgejo.nullbill.internal` on every tailnet device. The tailnet stage, after the policy, PATCHes Tailscale's split DNS so the plan's domain goes to `tailnet.nameserver` (the router's dnsmasq answers there already); an OAuth client without the `dns` scope (`MissingScope`) only says so and leaves names off, since addresses keep working. `$NULLBILL_HOME/names.json` records it, and the Services page then leads with names and keeps addresses as fallbacks. verify reads `tailscale dns status` on the vpn guest (its `--accept-dns=false` does not hide the tailnet's config): DEGRADED unless the domain goes to the router; and asks the router for `router.<domain>` from the vpn guest with `getent` (`names.ANSWERS`, FAIL without the right answer), the stretch of a device's lookup that lies on the server. The Tailscale app's "DNS unavailable" is the app's own (any forwarded lookup that timed out, cleared by the next answer) and no check's business; the page's Access, Tailscale tab says so.
- `ansible/roles/vpn`: pinned Tailscale in userspace networking (no tun in the container); logs in once with the owner's one-time auth key (`tailscale_auth_key`, pasted on the page, dropped by apply after login), then keeps routes and name with `tailscale set`. tailscaled listens on `flows.TAILSCALE_PORT` (41642, not Tailscale's default 41641, which a PC at home on Tailscale holds on the home router). From that port alone it may send UDP to private addresses past the router (router nftables and its pve-firewall file), so devices on the home network get a direct path; without it every byte went through a DERP relay and Jellyfin buffered.
- `ansible/`: host baseline (key-only SSH, auditd, no-subscription repo, security-only upgrades); `tools/check-host` runs it twice in a Debian 13 container (PVE 9's base; PVE 8 is past its end of life and refused) and checks the result. `docs/runbooks/` holds steps the owner does by hand. Guest roles carry `tests/check.sh`, which `tools/check-roles` runs under the Ansible apply pins (`requirements-apply.txt`, in a venv in the image; modules under the system Python) in a Debian 13 container, the release every Linux guest runs.
- `ansible/roles/router`: places `build/router` on the router VM, each nft and dnsmasq file checked before it replaces the old one; reboots when interface names change. Its check uses `tests/files`, which `tests/test_role_check_files.py` keeps equal to the small render.
- Direct connections (docs/adr/0014-direct-connections.md): a phone on mobile data reaches the vpn guest without a relay only on a port the home router forwards. The router's nftables DNATs UDP `flows.TAILSCALE_PORT` from the uplink to the vpn guest (sender's address kept) and the vpn guest's pve-firewall file accepts it, asked for or forwarded by hand. The router role's `nb-portmap` (`nullbill-portmap.timer`, every 15 minutes, a DynamicUser with `IPAddressDeny=` the network base) asks the home router for that port, NAT-PMP (spoken by `nb-portmap` itself, RFC 6886: Debian 13's natpmpc refuses a gateway whose address is not public) then UPnP with Debian's upnpc (`-z flows.SSDP_REPLY_PORT`, the one port the input chain takes UPnP's answer on), and writes what it heard to `/var/lib/nullbill-portmap/state.json` (a StateDirectory: `held` there names every mapping it may still hold, which must survive a restart, since some home routers keep a UPnP mapping until told otherwise); `tailnet.port_mapping: false` (the page's **Ask the home router for the port**, `/api/port-mapping`) makes it give back what it holds. `src/nullbill/direct.py` reads that file (`qm guest exec`) and `tailscale status --json` on the vpn guest through the host. Two things are kept apart. The port, as far as the server sees it (`Finding.kind`): direct, closed, shared (no public address: a provider's NAT or a second router), unseen, off; evidence only, since a port forwarded by hand or on a second router looks closed from in here. And the path, measured (`Finding.devices`): each device tailscaled sends to directly now (`CurAddr`), plus each device on the tailnet without a direct path, which the vpn guest pings (`ping_command`: `tailscale ping --c 3`, at most `MOST` at once; a CLI ping also makes both ends look for a direct path) and judges by the way its last answer came (`pongs`); a device that does not answer is left out, never called relayed. `verdict`: measured (a device direct from an address that is no home network's: PASS whatever the port says), open (PASS), relayed (a device answers only through a relay: DEGRADED), unmeasured (SKIP with what was read; a closed port alone is no finding). apply's vpn stage, verify (`devices on mobile data reach the vpn guest directly`) and the page record it in `$NULLBILL_HOME/direct.json` with `at` and `seen` (the last time a device away was direct); the page's Access, Tailscale tab (**Path**, **Devices**) reads it live while open (`/api/path`, `App.path`, cached 10 s, the last record with `live: false` while a job runs); only the kind of a device's address is kept, and the home's public address goes to neither the record nor a log. The page agent gets the same reading (`port_mapping` without `enabled`, `path_to_the_server` in `status`) and is told the switch is no fix for Path (`direct.SWITCH_MEANS`). `tools/guest-check/portmap.sh` (`tools/check-guests`) walks the path in network namespaces with the rendered ruleset, a NAT-PMP stand-in (`home-router`) and real miniupnpd on a shared address; upnpc and miniupnpd refuse documentation addresses, so UPnP's success is covered by `tests/test_portmap.py` with upnpc's real output.
- `ansible/roles/updates`: unattended-upgrades, needrestart and node_exporter with Debian's apt collector, plus `nb-update-metrics` (last successful run). apply's updates stage runs it on every Linux guest that lives on; `host_baseline` includes it for the host (security only, never reboots). Its alert rules are in the monitoring role's `nullbill.rules.yml`.
- Alerts: the monitoring role's Alertmanager sends every alert to `nb-alert-relay` (localhost), which posts to the owner's ntfy topic and turns the always-firing Watchdog into Healthchecks.io pings. The page makes the topic (`ntfy_topic` in secrets) when the owner sets a password and takes the optional `healthchecks_url`. `DiskAlmostFull` leaves kept disks and their copies out (`/mnt/nb-legacy/...`, `/srv/share/...`: the owner's own files); `KeptDiskFull` (warn) fires for a writable share with under 1 GiB left. Backup alerts read `host_baseline`'s hourly `nb-backup-metrics` (each nightly-job guest's newest encrypted backup on PBS, from `pvesh`); apply's backups stage runs it once after the first backups.
- `ansible/roles/console`: the optional on-site screen (`host.console`), cage and Chromium on the host's tty1 showing the page, its key pinned and every other address blocked by policy. apply's host stage runs it, on or off.
- `ansible/roles/downloads`: retries on a flaky line. Every role that installs packages depends on it (apt's `Acquire::Retries` with apt's growing pause); every pinned download goes through its `tasks_from: fetch` (get_url, checksum on each try). apt-get can wait forever after a refused redirect is retried, so its first task ends an apt-get older than `downloads_apt_stuck_minutes` (15) with no dpkg under it, which a stopped run leaves holding apt's lock. apply retries `tofu init` and an apply of the image downloads alone, 15/60/180 s apart, before the full apply, which runs once.
- `ansible/roles/egress_proxy`: Squid with the rendered `squid.conf`, each version checked before it replaces the last.
- `ansible/roles/pbs`: Proxmox Backup Server with a backup-only token for the host; its check backs up with client-side encryption, restores, and rebuilds over a kept datastore.
- `ansible/roles/tls_cert`: a step-ca certificate at `/etc/nullbill/tls/<name>.crt|.key`, first from a one-time token apply makes, then renewed by `step ca renew --daemon` (step-ca certificates last 24 h). Service roles (monitoring, postgres) read it from there and refuse to run without it; their checks seed those files from `test_pki`.
- `ansible/roles/forgejo`: Forgejo from a checksum-pinned release behind nginx (HTTPS on 443 with the browser CA's certificate for its name and address when apply passes one, else its tls_cert certificate; the browser root joins its system store), its own SSH server on 22 (no OpenSSH on that guest), PostgreSQL with `sslmode=verify-full`, no sign-up, Actions on. `nb-forgejo` runs its CLI as `git`. Its check runs the postgres role in the same container.
- `ansible/roles/runner_dispatcher` (`nb-dispatcher`) and `ansible/roles/ci_runner`: per queued Actions job, an ephemeral runner registration and a linked clone of the pool's golden image with a one-time nonce in its SMBIOS serial; the clone fetches its registration once from the dispatcher on 8443, runs `forgejo-runner one-job --handle` as `runner` and powers off; the dispatcher destroys it. The dispatcher's check runs a real job through Forgejo with `tests/fake_pve.py` standing in for PVE; `tests/test_dispatcher.py` covers the failure paths. Forgejo's name has the browser CA's certificate, so the dispatcher checks Forgejo with `forgejo-ca.pem` (step-ca's and the browser root, `apply.both_roots`) and the image trusts the browser root; `bake` records a digest of the image's inputs (`/root/nullbill/<pool>.inputs`) and bakes again when it changes.
- `ansible/roles/step_ca` also runs the `agent` provisioner: SSH user certificates for principal `agent` only, at most 1 h, no X.509. `ansible/roles/agent_ssh` makes agent-managed guests accept those for the unprivileged `agent` user and never for root.
- `ansible/roles/operator`: the agent user, its secrets (root-owned, agent-readable), the pinned agent CLI with root-owned managed settings and rules that list the guests (apply's `agent_map`), `nb-ssh` for agent-managed guests, and `nb-page`, which runs `nullbill verify` through the page's agent API (`/api/agent/*` in `web/server.py`: a token whose SHA-256 apply writes to `$NULLBILL_HOME/web/agent-token.sha256`, accepted from the operator's address only, verify and its output only) with the page's key pinned. Remote agents get the same API with a token each that the owner makes and revokes on the page (SHA-256 in `$NULLBILL_HOME/web/remote-agents.json`), accepted from the vpn guest's address only; requests are logged to the journal by agent name and jobs record `by`. The tailnet policy lets `tag:nb-agent` devices reach the page port only. Its check logs in end to end through the real CA.
- Command log: `agent_ssh` records each agent SSH command (`nb-agent-command`) and the operator's managed hook records each agent CLI tool call (`nb-log-tool-use`) in the journal before it runs, failing closed. `ansible/roles/log_shipper` ships those and sshd's auth lines to Loki with a shipper certificate, from the shipper guests and from the PVE host (host label `pve`; `log_shipper_resolve` puts the gate's name in the host's /etc/hosts, since its LAN resolver knows no NullBill names); the monitoring role's nginx gate takes pushes only with one, and refuses deletes. Trust the `uid` label (journald's), not the message text.
- `src/nullbill/backups.py`: the PBS storage and nightly job the OpenTofu render adds, and verify's backup-age and restore checks. Where the datastore lives (docs/adr/0017-backups-on-one-disk.md, docs/runbooks/backups.md): on a disk of PBS's own (pinned `use: pbs`, the disk already holding `nb-pbs-disk`, or a blank one; `backups.separate_disk` must agree with `plan._disks`) the plan's status is `ok` and the disk becomes the host's `nb-pbs-disk` LVM storage (`host_baseline`'s `nb-backup-disk`, run by the tofu stage, refuses signatures without `wipe`); without one it is `same-disk`: a volume on `plan.guest_storage` of `backups.SAME_DISK_GIB` (64, pin `backups.size_gib`), less when the disk has less after every guest's floor, and under `MIN_GIB` (16) `DEGRADED` with no pbs resources. plan reserves it before sizing pools. verify is DEGRADED for same-disk on every run and still runs every backup check. Either way the datastore is one disk of the pbs VM (serial `nb-backups`, `prevent_destroy`; `backups.store` gives OpenTofu its storage and size). When the plan's place or size differs from what `qm config` shows (`backups.datastore_disk`), the tofu stage's `place_datastore` moves the volume with `qm disk move --delete 1` while the VM runs and grows it with `qm disk resize` before OpenTofu compares, and the pbs role's `resize2fs` follows; a smaller size stops the run. `services.<name>.backup: false` leaves a guest out of the job and the checks (the catalog: `inference`; `backups.left_out` in the plan). apply's backups stage runs the pbs role, keeps PBS's token and fingerprint and the encryption key (made on the host, kept in sops) in secrets, re-runs tofu when they change and backs up each guest that has no backup yet. `host_baseline`'s hourly `nb-backup-metrics` also restores `etc/hostname` from one container's newest backup once per night's backups (another container each time, again each hour while it fails; state in `/var/lib/nullbill/restore-test.json`) and exports `nb_backup_restore_*`, `nb_backup_exists` and `nb_backup_store_bytes`; alerts `BackupRestoreFailing` (page) and `BackupStoreAlmostFull` (warn). The page's Backups page (`web/backupview.py`, `App.backups_view`, `/api/backups`; `backups` in /api/state): what the owner chose, what the last finished setup run built and what the host measured (from Prometheus, with `read`: when the host measured) are kept apart; POST turns backups on at a place (`system` with a size, a blank disk, or a disk to erase with the typed word through the page's own disk pin) and never turns them off, which deletes them and stays under Setup, What to run. `/api/backups/key` gives the signed-in owner the encryption key as a file and records the download with the key's fingerprint (`web/backup-key.json`, in `STAMPED`); the agent's `backups` tool reads the page without the key. Not tested on Proxmox VE: the move, the resize, a USB disk, the host's restore test.
- Kept disks (`disks.<id>.use: legacy`, docs/adr/0007-legacy-disks.md): `src/nullbill/legacy.py` plans which partitions are kept (NTFS, exFAT, FAT; Windows' EFI, MSR and recovery types skipped; ro unless pinned, rw NTFS only), their share names, and verify's checks (host mount mode and fstype, the guest's bind mount, Samba's settings). The probe reads partitions (`blkid`-level type, label, UUID), SMART and each disk's LVM volume groups (a disk holding `nb-pbs-disk` stays the PBS disk, and a storage disk its own group, without `wipe`); a disk mounted under `/mnt/nb-legacy` is not a system disk. apply's tofu stage runs `host_baseline`'s `nb-legacy-disk` (systemd mount unit by the partition's by-id name, never by UUID (clones share one), through ntfs-3g, immutable empty mount point, refuses rw on a hibernated, unclean or chkdsk-marked NTFS and checks the mode after mounting; never formats or repairs) before `nb-backup-disk`, records `$NULLBILL_HOME/disks.json` (which `backup_disk` refuses to wipe), and after tofu attaches bind mounts to the `files` LXC with `pct set` (OpenTofu ignores its mount points). The files stage runs `ansible/roles/files`: Samba, SMB3 with required encryption, one user `nbshare` (password `files_share_password` in secrets, shown on the page). `LegacyDiskMissing` reads `nb-legacy-disk metrics`; DiskAlmostFull skips kept disks and read-only filesystems (see Alerts). Read-write (2026-11-09): the probe's `ntfs` command (`probe.NTFS_CHECK`, three read-only ntfs-3g tools, fine on a mounted partition) gives each NTFS partition `rw_state` (clean, unclean, hibernated, chkdsk, damaged; None before ntfs-3g is on the host) and `journal`, a fingerprint of the journal's restart pages. plan refuses `mode: rw` on a known state other than clean, the page shows the state under What to run (`legacy.write_state`; "editable" from `disks.json`), and apply's `check_writable` reads it again before the files or Jellyfin guest stops (a mount refused later starts them again, `resume_guests`). Only `unclean` has a way without Windows: `disks.<id>.discard_journal: [<fingerprint>]` (the page: the id's last 6 characters typed) lets `nb-legacy-disk mount ... JOURNAL` run `ntfsfix -d` once when that very journal is still there, recorded in `/var/lib/nullbill/discarded-journals`; never for hibernated or chkdsk. `tools/host-check` writes such journals onto images itself (`open_journal`) and reads them through `probe.py` (`/src` mounted in). Converting a mounted kept disk to pbs needs `wipe` plus `evacuate: <lvm/lvmthin storage>` or `discard_data: true` (`legacy.plan_convert`; plan reserves the copies' room before sizing pools). With evacuate, the tofu stage first runs `host_baseline`'s `nb-legacy-copy` as a transient unit (files guest stopped): a new ext4 volume owned by the files guest, rsync, a tree compare plus a SHA-256 sample, and a record in `/var/lib/nullbill/kept-copies` only if it passes; `backup_disk` refuses a disk from `disks.json` unless every planned copy is recorded or the pin says `discard_data`. Copies are mounted rw in the files guest with `backup=1` (probe's `copies`), and the files guest gets `prevent_destroy`. `use: storage` (phase 3): `host_baseline`'s `nb-storage-disk` makes an LVM-thin PVE storage (`storage`, default `nb-data`) before tofu; guests stay on `plan.guest_storage`. A kept disk converted to storage with evacuate gets its copies back: `move_copies` runs `nb-legacy-copy move` (copy, check, then the record names the new volume), `attach_shares` swaps the mount point (copies are matched by guest path, so a copy the owner moved in PVE stays) and `free_moved` deletes the old volume once no mount point names it. The page's Setup, What to run, sets `disks` (erase, or copy then erase for a kept disk, needs the id's last 6 characters, checked by the server).
- Local models (docs/adr/0008-local-models.md): `src/nullbill/llm.py` and apply's inference stage. plan picks the largest of `catalog.yaml`'s `models` (Hugging Face commit + SHA-256, `vram_mib`, and the model card's `sampling`, `reasoning`, `reasoning_effort` and `cache_type`, which the unit passes to llama-server: without them Qwen3.5 ran with generic sampling and no thinking, and looped) that fits the inference VRAM budget (`inference.model` pins); NVIDIA only, llama.cpp only (vLLM not built). `ansible/roles/nvidia_host` installs the pinned `.run` with DKMS and open modules on the host (release pinned only there; nouveau held means one restart; `nb-nvidia-devices` makes `/dev/nvidia*` before guests start). apply sets the inference container's `devN` as root (OpenTofu ignores `device_passthrough`), lifts its memory to `BUILD_MEMORY_MIB` while `ansible/roles/inference` runs (NVIDIA user space `--no-kernel-modules`, llama.cpp built from a tag checked against its commit with the Vulkan backend against Debian 13's Vulkan headers; one file needs 1.8 GiB to compile), then `ansible/roles/model_gateway`: LiteLLM from a hash-pinned lock (`files/requirements.txt`, uv command in its defaults) behind nginx on 4000 with a tls_cert certificate, model offered by name and as `local`, keys `model_gateway_key` (page, Services) and `inference_key` in secrets; build-zone containers get step-ca's root. The inference check serves a tiny model on Mesa's lavapipe (`GGML_VK_VISIBLE_DEVICES`). verify: driver version and model in VRAM on the host, an answer and a refused key through the gateway.
- Jellyfin (docs/adr/0009-media-server.md): `src/nullbill/media.py`, the `media` workload alone in the `media` zone (proxy egress). Its library is the kept disks' shares, bind-mounted `ro=1` at `/media/<share>` by the tofu stage (`attach_media`; `detach_media` and `stop_media` before the host unmounts, as for the files guest). Runs as uid 1000, which owns the kept disks' files. Transcodes with Quick Sync on the integrated Intel GPU the probe finds (render node by `by-path` as `devN`, gid 1000), else on the CPU (`media.transcode: cpu` pins). apply's media stage runs `ansible/roles/jellyfin` (pinned packages from Jellyfin's repository), then `nb-jellyfin` finishes the first-run setup at once (admin `nullbill-admin`, password and an API key root-only in `/etc/nullbill/` in the guest; `jellyfin_admin_password` in secrets) and sets transcoding. Jellyfin answers camelCase unless asked `profile="PascalCase"`, and a stand-in answers while it first starts. Its check runs Jellyfin and nb-jellyfin for real; verify checks the setup is closed, the disks read-only and Quick Sync through `vainfo`.

none, no upgrade), then for a container with less, `release.MEMORY_MIB` of memory while it is upgraded (`lend_memory`, its own again after; the controller's by `tools/upgrade-controller`'s last argument): the kernel ended dpkg in the vpn guest's 256 MiB on the first real run, `data/nb-release-upgrade` as a transient unit in the guest (downloads everything first, keeps settings files, holds every package of a vendor's repository while it runs so that none passes its pin (Debian's own are told by the Release file's `Origin`, not the address: a cloud image VM reads them through `mirror+file:`, and the first real run held all of the router's), moves a PostgreSQL cluster with `pg_upgradecluster` and keeps the old one stopped), polled through its result file, then a restart and a look; a failure, a silent guest after the restart included, rolls the guest back and stops the run. A guest whose copy is a backup is not put back; a result file whose last line is not `done` stops the stage before the copy is touched, until the owner restored the guest. `$NULLBILL_HOME/releases.json` records each guest (the page's review reason and the nightly's wait read `release.unknown`, never the server); snapshots are deleted a week on (`drop_copies`). Left out: Windows, pool images (the bake's input digest carries the release, so the ci stage makes them again), pbs, the owner's own services, and install.sh's container, which `controller_release` upgrades last by `tools/upgrade-controller` as a unit of its own after a full run (rollback asked of the host on failure, the log copied to the host first; `controller-release.json`, written before the snapshot, stops a second try by itself and dates the snapshot's deletion). `run_apply` refuses one stage alone (`BEFORE_RELEASE` excepted) while guests from before wait. The postgres role stops beside an older version's cluster that was not moved. `tools/check-release` upgrades a real Debian 12 container (PostgreSQL 15 with data) and one set up as the controller. Not tested on Proxmox VE: snapshots and rollback, `qm guest exec --pass-stdin`, systemd's own upgrade under the unit in an unprivileged container, the controller's restart.

The page: `App.foresee` (`machines` in the review), `App.update_effect` (`effect` in `version`), `renderReview` and `renderUpdateEffect` in `app.js` (`machineRows`: one line per machine the run touches, what interrupts first, with the row's `effect` (a few words from `preview.in_short`: "Minecraft may restart", "Nothing restarts") and `interrupts`; why, the programs and the last run's time open under the line, as on the Services page; the rest by name under "Left alone" and "Not known"; the owner called a row of sentences per machine "so long, ugly and pointlessly hard to read", so nothing more goes into the closed row); the agent's `status` carries both (`chat.foreseen`). Wording: "may restart", never "restarts" (Ansible restarts a unit only when the file on the machine differs), and a machine no run has written down is "Not known", never left alone. ## Privacy rules (public repo)

- Never commit secrets, real hostnames, IPs, MACs, usernames, emails, serials,
  licence keys or real probe output. Use `example.internal`, RFC 1918 or
  RFC 5737 addresses, placeholder names and synthetic hardware.
- Owner data lives in `$NULLBILL_HOME` outside the repo: `config.yaml`,
  `probe/`, `plan.yaml`, `denylist.txt`, later tofu state and sops files.
- The pre-push hook fails without a non-empty `$NULLBILL_HOME/denylist.txt`.
- When unsure whether something identifies the owner, leave it out and ask.

## Commits and PRs

- Author commits with the owner's GitHub noreply address; no
  `Co-Authored-By`, `Claude-Session` or "Generated with Claude Code" lines.
  `.claude/settings.json` turns that attribution off.
- Commit messages state the change and the reason.
- No stubs committed as done. Unfinished work is an issue. No figures that a
  script in this repo cannot reproduce.

## Working with the owner

- Questions go in `OPEN_QUESTIONS.md`, each with a one-line recommendation.
- Owner approval before anything public, anything that spends money, or any
  tool change (with an ADR draft in `docs/adr/`).
- Nothing touches real hardware without the owner's go for that milestone.
