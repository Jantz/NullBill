# CLAUDE.md

Guidance for Claude sessions working in this repository.

## What this is

NullBill turns a spare x86 machine running Proxmox VE into a self-hosted dev
server from one declarative config. `nullbill` runs on a controller the owner
names and reaches the host over SSH; it never runs on the host. Only `probe`,
`plan`, `apply` (stages so far: render, tailnet, host, tofu, router, proxy, updates, ca, postgres, monitoring, forgejo, inference, files, media, games, ci, agents, logs, backups, vpn, verify),
`verify` and `upgrade` exist.

## Layout

- `src/nullbill/data/catalog.yaml`: platform defaults (zones, roles, services, engine table).
- `src/nullbill/data/schema.yaml`: JSON Schema for `config.yaml` and for the merged model.
- `src/nullbill/probe.py`: read-only probe commands and their parser.
- `src/nullbill/plan.py`: sizing rules; every rule failure is collected and reported together. Memory: VMs count in full, containers at `host.container_share_pct` (50) of their limit, since an LXC limit is not a reservation; `HostMemoryLow` alerts when that bet fails. A GPU's VRAM is needed only when inference budgets it; the page asks for it when the probe (no driver yet) cannot read it.
- `tests/fixtures/<class>.yaml`: synthetic probe output for small, mid, large.
- `tests/golden/<class>.plan.yaml`: expected plans. Regenerate with `UPDATE_GOLDEN=1 python3 -m pytest` and review the diff.
- `hooks/`, `tools/denylist-scan`: privacy hooks. `tools/install-hooks` enables them.
- `src/nullbill/flows.py`: the one flow list both firewall layers are generated from.
- `src/nullbill/firewall.py`: pve-firewall files (`host.fw` goes to `/etc/pve/local`, the rest to `/etc/pve/firewall`); `tools/check-firewall` parses and compiles them with the stock pve-firewall in a container and runs PVE's simulator (LAN to 8006/22 dropped only when closed; the closed `cluster.fw` sets `local_network` to the vpn guest, since PVE adds that alias to `management`).
- `src/nullbill/router.py`, `src/nullbill/proxy.py`: router (nftables, dnsmasq, interfaces) and Squid files; `tools/check-guests` checks them with Debian 12's nft, dnsmasq, ifupdown and squid.
- `src/nullbill/lan.py`: closing the LAN to 8006 and 22 (#9). `apply --close-lan` (host stage only) arms a 15-minute systemd-run timer on the host that restores `/root/nullbill/cluster-lan-open.fw` (and a marker that `nb-lan-revert-boot.service` acts on at boot, since the timer does not survive a restart), then installs the closed cluster.fw; `--confirm-lan` stops the timer and removes the marker, and the page runs it only for a request from the vpn guest's address. State in `$NULLBILL_HOME/lan.json`; while closing or closed the controller reaches the host at its mgmt address, verify checks the LAN address (DEGRADED while open), and once closed the page refuses clients outside the network base.
- `src/nullbill/tailnet.py`: Tailscale policy from people and roles, the only per-person gate; plan fails past the free-plan limits in `catalog.yaml`. A person's `services` become a grant from their login (no group: only a role that is held and named by a port gets one), and each person gets a policy test: accepted on what they hold, denied on the host, the router and every other person-facing port. `routes` are the zones the vpn guest advertises. Every group and every person may reach the router's access-zone leg (`tailnet.nameserver`) on 53, which the vpn guest advertises as a /32.
- People (docs/adr/0011-people.md, docs/runbooks/add-person.md): `src/nullbill/people.py` and the page's Access, People tab (`/api/people`, `/remove`, `/sync` in `web/server.py`). A port can be given to a person only if its `from` lists `shared` (never in mgmt); `shared` opens the firewall from the vpn guest like a role, whoever holds it, so a person more or less changes `tailnet/policy.json` only and needs no setup run. The page pushes to Tailscale first (`tailscale.sync_policy`: validate with tests, set with the ETag, read back) and writes `config.yaml` only after, keeping its mtime so no setup run is asked for; before the first setup run or without an OAuth client it only saves. Invitations to the tailnet cannot be made with an OAuth client, so the owner sends them from Tailscale's Users page and the page writes what to send the person (each service's `share` block in the catalog). Removing deletes the Tailscale user when the client holds `users`. verify: `Tailscale holds each person to the services picked for them` compares the live policy with the rendered one (SKIP without a client).
- `src/nullbill/tailscale.py`: Tailscale's API with the owner's OAuth client (`tailscale_client_id`/`_secret` in secrets, pasted on the page). apply's tailnet stage, before the host stage, counts tagged devices, has Tailscale validate and test the rendered policy, pushes it with the read ETag and reads it back; any failure stops apply. The vpn stage runs only once that policy is in place. `NULLBILL_TAILSCALE_API` points it at a stand-in.
- `src/nullbill/names.py`: names such as `forgejo.nullbill.internal` on every tailnet device. The tailnet stage, after the policy, PATCHes Tailscale's split DNS so the plan's domain goes to `tailnet.nameserver` (the router's dnsmasq answers there already); an OAuth client without the `dns` scope (`MissingScope`) only says so and leaves names off, since addresses keep working. `$NULLBILL_HOME/names.json` records it, and the Services page then leads with names and keeps addresses as fallbacks. verify reads `tailscale dns status` on the vpn guest (its `--accept-dns=false` does not hide the tailnet's config): DEGRADED unless the domain goes to the router.
- `ansible/roles/vpn`: pinned Tailscale in userspace networking (no tun in the container); logs in once with the owner's one-time auth key (`tailscale_auth_key`, pasted on the page, dropped by apply after login), then keeps routes and name with `tailscale set`. tailscaled listens on `flows.TAILSCALE_PORT` (41642, not Tailscale's default 41641, which a PC at home on Tailscale holds on the home router). From that port alone it may send UDP to private addresses past the router (router nftables and its pve-firewall file), so devices on the home network get a direct path; without it every byte went through a DERP relay and Jellyfin buffered.
- `ansible/`: host baseline (key-only SSH, auditd, no-subscription repo, security-only upgrades); `tools/check-host` runs it twice in a Debian 13 container (PVE 9's base; PVE 8 is past its end of life and refused) and checks the result. `docs/runbooks/` holds steps the owner does by hand. Guest roles carry `tests/check.sh`, which `tools/check-roles` runs in a Debian 12 container, or Debian 13 for the roles in its `trixie_roles` (pbs: PBS 4 needs Debian 13, so the pbs VM boots catalog.yaml's `debian-13-cloud`).
- `ansible/roles/router`: places `build/router` on the router VM, each nft and dnsmasq file checked before it replaces the old one; reboots when interface names change. Its check uses `tests/files`, which `tests/test_role_check_files.py` keeps equal to the small render.
- Direct connections (docs/adr/0014-direct-connections.md): a phone on mobile data reaches the vpn guest without a relay only on a port the home router forwards. The router's nftables DNATs UDP `flows.TAILSCALE_PORT` from the uplink to the vpn guest (sender's address kept) and the vpn guest's pve-firewall file accepts it, asked for or forwarded by hand. The router role's `nb-portmap` (`nullbill-portmap.timer`, every 15 minutes, a DynamicUser with `IPAddressDeny=` the network base) asks the home router for that port, NAT-PMP then UPnP, with Debian's natpmpc and upnpc (`-z flows.SSDP_REPLY_PORT`, the one port the input chain takes UPnP's answer on), and writes what it heard to `/var/lib/nullbill-portmap/state.json` (a StateDirectory: `held` there names every mapping it may still hold, which must survive a restart, since some home routers keep a UPnP mapping until told otherwise); `tailnet.port_mapping: false` (the page's **Ask the home router for the port**, `/api/port-mapping`) makes it give back what it holds. `src/nullbill/direct.py` reads that file (`qm guest exec`) and `tailscale status --json` on the vpn guest through the host and judges: direct, closed, shared (no public address: a provider's NAT or a second router), unseen, off. apply's vpn stage and verify (`devices on mobile data reach the vpn guest directly`, DEGRADED unless direct, SKIP when off) record it in `$NULLBILL_HOME/direct.json` for the page's Access, Tailscale tab (**Path**); the home's public address goes to neither the record nor a log. `tools/guest-check/portmap.sh` (`tools/check-guests`) walks the path in network namespaces with the rendered ruleset, a NAT-PMP stand-in (`home-router`) and real miniupnpd on a shared address; upnpc and miniupnpd refuse documentation addresses, so UPnP's success is covered by `tests/test_portmap.py` with upnpc's real output.
- `ansible/roles/updates`: unattended-upgrades, needrestart and node_exporter with Debian's apt collector, plus `nb-update-metrics` (last successful run). apply's updates stage runs it on every Linux guest that lives on; `host_baseline` includes it for the host (security only, never reboots). Its alert rules are in the monitoring role's `nullbill.rules.yml`.
- Alerts: the monitoring role's Alertmanager sends every alert to `nb-alert-relay` (localhost), which posts to the owner's ntfy topic and turns the always-firing Watchdog into Healthchecks.io pings. The page makes the topic (`ntfy_topic` in secrets) when the owner sets a password and takes the optional `healthchecks_url`. Backup alerts read `host_baseline`'s hourly `nb-backup-metrics` (each nightly-job guest's newest encrypted backup on PBS, from `pvesh`); apply's backups stage runs it once after the first backups.
- `ansible/roles/console`: the optional on-site screen (`host.console`), cage and Chromium on the host's tty1 showing the page, its key pinned and every other address blocked by policy. apply's host stage runs it, on or off.
- `ansible/roles/downloads`: retries on a flaky line. Every role that installs packages depends on it (apt's `Acquire::Retries` with apt's growing pause); every pinned download goes through its `tasks_from: fetch` (get_url, checksum on each try). apt-get can wait forever after a refused redirect is retried, so its first task ends an apt-get older than `downloads_apt_stuck_minutes` (15) with no dpkg under it, which a stopped run leaves holding apt's lock. apply retries `tofu init` and an apply of the image downloads alone, 15/60/180 s apart, before the full apply, which runs once.
- `ansible/roles/egress_proxy`: Squid with the rendered `squid.conf`, each version checked before it replaces the last.
- `ansible/roles/pbs`: Proxmox Backup Server with a backup-only token for the host; its check backs up with client-side encryption, restores, and rebuilds over a kept datastore.
- `ansible/roles/tls_cert`: a step-ca certificate at `/etc/nullbill/tls/<name>.crt|.key`, first from a one-time token apply makes, then renewed by `step ca renew --daemon` (step-ca certificates last 24 h). Service roles (monitoring, postgres) read it from there and refuse to run without it; their checks seed those files from `test_pki`.
- `ansible/roles/forgejo`: Forgejo from a checksum-pinned release behind nginx (HTTPS on 443 with the browser CA's certificate for its name and address when apply passes one, else its tls_cert certificate; the browser root joins its system store), its own SSH server on 22 (no OpenSSH on that guest), PostgreSQL with `sslmode=verify-full`, no sign-up, Actions on. `nb-forgejo` runs its CLI as `git`. Its check runs the postgres role in the same container.
- `ansible/roles/runner_dispatcher` (`nb-dispatcher`) and `ansible/roles/ci_runner`: per queued Actions job, an ephemeral runner registration and a linked clone of the pool's golden image with a one-time nonce in its SMBIOS serial; the clone fetches its registration once from the dispatcher on 8443, runs `forgejo-runner one-job --handle` as `runner` and powers off; the dispatcher destroys it. The dispatcher's check runs a real job through Forgejo with `tests/fake_pve.py` standing in for PVE; `tests/test_dispatcher.py` covers the failure paths. Forgejo's name has the browser CA's certificate, so the dispatcher checks Forgejo with `forgejo-ca.pem` (step-ca's and the browser root, `apply.both_roots`) and the image trusts the browser root; `bake` records a digest of the image's inputs (`/root/nullbill/<pool>.inputs`) and bakes again when it changes.
- `ansible/roles/step_ca` also runs the `agent` provisioner: SSH user certificates for principal `agent` only, at most 1 h, no X.509. `ansible/roles/agent_ssh` makes agent-managed guests accept those for the unprivileged `agent` user and never for root.
- `ansible/roles/operator`: the agent user, its secrets (root-owned, agent-readable), the pinned agent CLI with root-owned managed settings and rules that list the guests (apply's `agent_map`), `nb-ssh` for agent-managed guests, and `nb-page`, which runs `nullbill verify` through the page's agent API (`/api/agent/*` in `web/server.py`: a token whose SHA-256 apply writes to `$NULLBILL_HOME/web/agent-token.sha256`, accepted from the operator's address only, verify and its output only) with the page's key pinned. Remote agents get the same API with a token each that the owner makes and revokes on the page (SHA-256 in `$NULLBILL_HOME/web/remote-agents.json`), accepted from the vpn guest's address only; requests are logged to the journal by agent name and jobs record `by`. The tailnet policy lets `tag:nb-agent` devices reach the page port only. Its check logs in end to end through the real CA.
- Command log: `agent_ssh` records each agent SSH command (`nb-agent-command`) and the operator's managed hook records each agent CLI tool call (`nb-log-tool-use`) in the journal before it runs, failing closed. `ansible/roles/log_shipper` ships those and sshd's auth lines to Loki with a shipper certificate, from the shipper guests and from the PVE host (host label `pve`; `log_shipper_resolve` puts the gate's name in the host's /etc/hosts, since its LAN resolver knows no NullBill names); the monitoring role's nginx gate takes pushes only with one, and refuses deletes. Trust the `uid` label (journald's), not the message text.
- `src/nullbill/backups.py`: the PBS storage and nightly job the OpenTofu render adds, and verify's backup-age and restore checks. The pinned disk becomes the host's `nb-pbs-disk` LVM storage (`host_baseline`'s `nb-backup-disk`, run by the tofu stage, refuses signatures without `wipe`); the pbs VM's datastore disk lives there (serial `nb-backups`, `prevent_destroy`). apply's backups stage runs the pbs role, keeps PBS's token and fingerprint and the encryption key (made on the host, kept in sops) in secrets, re-runs tofu when they change and backs up each guest that has no backup yet.
- Kept disks (`disks.<id>.use: legacy`, docs/adr/0007-legacy-disks.md): `src/nullbill/legacy.py` plans which partitions are kept (NTFS, exFAT, FAT; Windows' EFI, MSR and recovery types skipped; ro unless pinned, rw NTFS only), their share names, and verify's checks (host mount mode and fstype, the guest's bind mount, Samba's settings). The probe reads partitions (`blkid`-level type, label, UUID), SMART and each disk's LVM volume groups (a disk holding `nb-pbs-disk` stays the PBS disk, and a storage disk its own group, without `wipe`); a disk mounted under `/mnt/nb-legacy` is not a system disk. apply's tofu stage runs `host_baseline`'s `nb-legacy-disk` (systemd mount unit by the partition's by-id name, never by UUID (clones share one), through ntfs-3g, immutable empty mount point, refuses rw on a hibernated, unclean or chkdsk-marked NTFS and checks the mode after mounting; never formats or repairs) before `nb-backup-disk`, records `$NULLBILL_HOME/disks.json` (which `backup_disk` refuses to wipe), and after tofu attaches bind mounts to the `files` LXC with `pct set` (OpenTofu ignores its mount points). The files stage runs `ansible/roles/files`: Samba, SMB3 with required encryption, one user `nbshare` (password `files_share_password` in secrets, shown on the page). `LegacyDiskMissing` reads `nb-legacy-disk metrics`; DiskAlmostFull skips read-only filesystems. Read-write (2026-11-09): the probe's `ntfs` command (`probe.NTFS_CHECK`, three read-only ntfs-3g tools, fine on a mounted partition) gives each NTFS partition `rw_state` (clean, unclean, hibernated, chkdsk, damaged; None before ntfs-3g is on the host) and `journal`, a fingerprint of the journal's restart pages. plan refuses `mode: rw` on a known state other than clean, the page shows the state under What to run (`legacy.write_state`; "editable" from `disks.json`), and apply's `check_writable` reads it again before the files or Jellyfin guest stops (a mount refused later starts them again, `resume_guests`). Only `unclean` has a way without Windows: `disks.<id>.discard_journal: [<fingerprint>]` (the page: the id's last 6 characters typed) lets `nb-legacy-disk mount ... JOURNAL` run `ntfsfix -d` once when that very journal is still there, recorded in `/var/lib/nullbill/discarded-journals`; never for hibernated or chkdsk. `tools/host-check` writes such journals onto images itself (`open_journal`) and reads them through `probe.py` (`/src` mounted in). Converting a mounted kept disk to pbs needs `wipe` plus `evacuate: <lvm/lvmthin storage>` or `discard_data: true` (`legacy.plan_convert`; plan reserves the copies' room before sizing pools). With evacuate, the tofu stage first runs `host_baseline`'s `nb-legacy-copy` as a transient unit (files guest stopped): a new ext4 volume owned by the files guest, rsync, a tree compare plus a SHA-256 sample, and a record in `/var/lib/nullbill/kept-copies` only if it passes; `backup_disk` refuses a disk from `disks.json` unless every planned copy is recorded or the pin says `discard_data`. Copies are mounted rw in the files guest with `backup=1` (probe's `copies`), and the files guest gets `prevent_destroy`. `use: storage` (phase 3): `host_baseline`'s `nb-storage-disk` makes an LVM-thin PVE storage (`storage`, default `nb-data`) before tofu; guests stay on `plan.guest_storage`. A kept disk converted to storage with evacuate gets its copies back: `move_copies` runs `nb-legacy-copy move` (copy, check, then the record names the new volume), `attach_shares` swaps the mount point (copies are matched by guest path, so a copy the owner moved in PVE stays) and `free_moved` deletes the old volume once no mount point names it. The page's Setup, What to run, sets `disks` (erase, or copy then erase for a kept disk, needs the id's last 6 characters, checked by the server).
- Local models (docs/adr/0008-local-models.md): `src/nullbill/llm.py` and apply's inference stage. plan picks the largest of `catalog.yaml`'s `models` (Hugging Face commit + SHA-256, `vram_mib`, and the model card's `sampling`, `reasoning`, `reasoning_effort` and `cache_type`, which the unit passes to llama-server: without them Qwen3.5 ran with generic sampling and no thinking, and looped) that fits the inference VRAM budget (`inference.model` pins); NVIDIA only, llama.cpp only (vLLM not built). `ansible/roles/nvidia_host` installs the pinned `.run` with DKMS and open modules on the host (release pinned only there; nouveau held means one restart; `nb-nvidia-devices` makes `/dev/nvidia*` before guests start). apply sets the inference container's `devN` as root (OpenTofu ignores `device_passthrough`), lifts its memory to `BUILD_MEMORY_MIB` while `ansible/roles/inference` runs (NVIDIA user space `--no-kernel-modules`, llama.cpp built from a tag checked against its commit with the Vulkan backend against pinned Vulkan-Headers, since Debian 12's are too old; one file needs 1.8 GiB to compile), then `ansible/roles/model_gateway`: LiteLLM from a hash-pinned lock (`files/requirements.txt`, uv command in its defaults) behind nginx on 4000 with a tls_cert certificate, model offered by name and as `local`, keys `model_gateway_key` (page, Services) and `inference_key` in secrets; build-zone containers get step-ca's root. The inference check serves a tiny model on Mesa's lavapipe (`GGML_VK_VISIBLE_DEVICES`). verify: driver version and model in VRAM on the host, an answer and a refused key through the gateway.
- Jellyfin (docs/adr/0009-media-server.md): `src/nullbill/media.py`, the `media` workload alone in the `media` zone (proxy egress). Its library is the kept disks' shares, bind-mounted `ro=1` at `/media/<share>` by the tofu stage (`attach_media`; `detach_media` and `stop_media` before the host unmounts, as for the files guest). Runs as uid 1000, which owns the kept disks' files. Transcodes with Quick Sync on the integrated Intel GPU the probe finds (render node by `by-path` as `devN`, gid 1000), else on the CPU (`media.transcode: cpu` pins). apply's media stage runs `ansible/roles/jellyfin` (pinned packages from Jellyfin's repository), then `nb-jellyfin` finishes the first-run setup at once (admin `nullbill-admin`, password and an API key root-only in `/etc/nullbill/` in the guest; `jellyfin_admin_password` in secrets) and sets transcoding. Jellyfin answers camelCase unless asked `profile="PascalCase"`, and a stand-in answers while it first starts. Its check runs Jellyfin and nb-jellyfin for real; verify checks the setup is closed, the disks read-only and Quick Sync through `vainfo`.
- Game servers (docs/adr/0012-game-servers.md, docs/runbooks/games.md): `src/nullbill/games.py` and `catalog.yaml`'s `games` table (minecraft, terraria, factorio), each a service and workload of the same name, one unprivileged container in the `games` zone (proxy egress), one player port whose `from` is the owner and `shared` (friends get a game under Access, People; `share` text takes `{port}` and `{version}`). The server is the vendor's own file pinned by SHA-256 (`tools/game-pins` prints what the vendors offer now; `games.<name>` in config.yaml overrides a pin), `games.<name>.settings` are the server's own options and plan refuses those in `games.MANAGED` (port, public listing, account checks). plan refuses Minecraft without `games.minecraft.eula: true` (the page asks beside the tick, with admins: `server._games_config`); Minecraft's heap is the container's memory less `JVM_OVERHEAD_MIB`. apply's games stage runs `ansible/roles/game_<name>` (each depends on `game_server`: user `game`, `nb-game`, a metrics timer, `/etc/nullbill/busy.d/game`), waits with `nb-game wait`, then types `op`/`/promote` on the console for admins the server lacks (added only, never removed). Every server runs under a unit whose stdin is a FIFO in its runtime directory and which saves on stop (`stop`, `exit`, SIGTERM); `nb-game` (status, players, wait, console, stop, admins, busy, metrics) counts players by Minecraft's status ping, Terraria's established TCP connections, Factorio's RCON on 127.0.0.1. Minecraft ignores proxy settings, so `nb-tls-tunnel` on 127.0.0.1:443 relays each TLS hello's name to the egress proxy with CONNECT and Java's own hosts file (`jdk.net.hosts.file`) points Mojang's names there; the server rewrites `server.properties`, so `nb-properties` sets keys in place. Factorio's `nb-factorio-mods` turns the Space Age mods on or off (`games.factorio.space_age`). The checks run the real servers with the `game` user cut off from all but loopback (`loopback_only`, `start_game`, `game_says` in `role-check.sh`) behind `game_server/tests/connect-proxy.py`; each role's `tests/vars.json` equals what `games.variables` gives the `large-games` fixture (`tests/test_games.py`). verify: version and answer per game, Mojang through the tunnel, admins; the UDP path to Factorio is not probed. Alert `GameServerDown` reads `nb_game_up`. Terraria's version (1.4.5.8) has an address's shape, so `.gitleaks.toml` allows `1.4.<digit>.<digit>`.
- On demand (docs/adr/0013-on-demand.md, docs/runbooks/on-demand.md): `src/nullbill/power.py`. `power.<workload>` in the catalog, pinned in config.yaml (`run: always|on-demand`, `stop: auto|ask|manual`, `idle_minutes`, `busy.cpu_pct`); a workload without an entry gets `model.POWER_DEFAULTS` (ask after 2 h). plan counts what always runs as before and asks of each on-demand workload only that it fits beside that (`power.headroom_mib`, `together`); OpenTofu makes such guests `started = false`, no start at boot, `started` ignored. `host_baseline`'s `nb-power` (rules in `/etc/nullbill/power.json` from apply's host stage, a timer every minute, state in `/var/lib/nullbill/power.json`, metrics `nb_power_*`) is the only thing that starts and stops them: `start` (exit 3 with what would have to stop when it does not fit; never stops what is in use or `ask`/`manual` without `--stop`), `stop`, `keep`, `tick` (stops `auto` workloads idle for their minutes, marks `ask` ones for the `OnDemandLeftOn` alert), and for apply `ensure <guest>..` and `setup end`. Use is what each guest's `nb-busy` (updates role) prints: SSH, tmux, apt at work, the programs a service's role puts in `/etc/nullbill/busy.d` (Jellyfin, model gateway, Samba, a game's `nb-game busy`), else TCP connections to the service's ports; a pool counts while a clone runs; a probe that fails counts as use. A new workload joins with a `power` entry and a `busy.d` program (UDP-only services need one). apply reaches an on-demand guest only through `ensure_on` (`run_playbooks`, `guest_out`, `vm_out`; `batches` runs a playbook one workload at a time when the plan says not everything fits) and `end_hold` in `run_apply`'s `finally` stops again what was off. verify reads `nb-power status` once and reports SKIP for checks from, to or inside a guest that is off (`power.guard` raises `Off` for `pct exec` into one; `unless_off` wraps a module's checks, and a module that reaches several workloads or the host too, as games and legacy do, catches `Off` per check); it never starts one. `TargetDown` and the certificate alerts leave out `nb_power_guest_off`. The page: `web/demand.py`, `/api/on-demand` (GET is `nb-power status` over SSH, cached 5 s, asked only on the Services page; POST start/stop/keep, where a start that does not fit and a stop of something in use change nothing and come back as questions), `power` rows in `workloads.options` (Setup, What to run, When it runs; `_power_pins` saves only what differs from the catalog) and `off`/`asks` in `/api/status` from Prometheus. The page agent's gate reads `nb-power status` and treats the rest as a change.
- Owner's switch (docs/adr/0003-agent-access.md, 2026-11-08): `src/nullbill/hostroot.py` puts the operator's key (`~agent/.ssh/nb-host`, made by the operator role, public half in `$NULLBILL_HOME/web/agent-host-key.pub` from the agents stage) in the host's authorized_keys, `from=` the operator, `command=` `nb-agent-command` (host_baseline installs it); the page's Agents page toggles it (`/api/agent-powers`, state in `$NULLBILL_HOME/web/agent-powers.json`; off removes the line first and stays off on failure), and while on the operator may also POST `/api/agent/apply` (`stage`) and `/api/agent/upgrade` and read every job; each such job and its end go to ntfy, and a job it cannot announce does not start. verify: `the agent has no root on the PVE host` DEGRADED while on. The operator's `ssh pve` pins the host key. A GitHub token (`agent_github_token`, checked with GitHub on the page) gives the agent `gh`/git push for PRs with the owner's noreply identity; apply's `agent_denylist` (LAN address, logins, disk ids, partition UUIDs and labels, the owner's denylist.txt) feeds the repo's pre-push hook there.
- `src/nullbill/browserca.py` (docs/runbooks/trust-this-server.md): the browser CA, an openssl CA in `$NULLBILL_HOME/browser-ca/` with critical name constraints (plan domain and `network.base`), whose root the page serves at `/nullbill-root.crt` (no sign-in) for the owner's devices; step-ca's root is unconstrained and never offered. It signs, by address and name, 825 days, renewed under 90: the page (apply's ca stage re-signs `web/cert.pem` for the same key, so SPKI pins hold; the server reloads it within a minute), Forgejo (every request, by name too: people and runners share the name; monitoring's certificate probes trust both roots, `apply.both_roots`), the model gateway (nginx `default_server`, for clients sending no SNI, so Page Assist uses the address; named clients keep step-ca's), Grafana (now HTTPS on 3000 through nginx, Grafana on 127.0.0.1:3001), and Proxmox only while `lan.json` says closed (`host_baseline`'s `nb-pve-api-cert` with CERT KEY; open, it is PVE's CA again, since apply reaches 8006 at the LAN address the root cannot name). PVE API clients (tofu, operator, dispatcher) trust both roots (`apply.pve_ca`). verify: `browsers trust the page` / `Proxmox` by address and by name with curl from the host, Forgejo and Grafana by name from inside their guests (DEGRADED).
- `src/nullbill/owner.py`: the owner's own accounts. SSH public keys pasted on the page (Access, SSH keys; `/api/ssh-keys`) are `people.<owner>.ssh_keys`; the agents stage puts them on the workspace (root's authorized_keys between `# nullbill:` lines, even without an agent credential) and the forgejo stage runs `nb-forgejo-owner`, which makes the owner's own Forgejo administrator once (name from the Tailscale login, kept as `forgejo_owner_user`; password `forgejo_owner_password`, no forced change) and keeps its `nullbill: ` titled keys equal to the page's through the API with a root-only nullbill-admin token. The media stage's `nb-jellyfin library` adds each kept disk as a mixed library once (a marker keeps a removed one removed). The Services page's entries carry `steps` (text, `done`, link, code to copy) for setting each one up.
- `src/nullbill/upgrade.py`: `nullbill upgrade` (the page's **Update NullBill**, on its Updates page) fetches main into `/opt/nullbill`, refuses local changes or going back, checks it out, records what it moved from and to (`$NULLBILL_HOME/web/last-update.json`) and runs `tools/finish-upgrade` with `systemd-run` (outside the page's ProtectSystem and cgroup): setup-controller, the unit file, a restart of the page.
- Updates and the review before setup: `src/nullbill/version.py` reads the checkout with git: the commit that runs, what origin's main holds beyond it (`fetch`, by the page once a day and on **Check for updates**; `web/update-check.json`), and per commit whether it changes what setup builds (it touches `SETUP_PATHS` outside `NOT_SETUP`; a new module that setup does not read goes into `NOT_SETUP`). Each full setup run (`apply` or `remove-guests` without `--stage`: `App.setup_runs`) records the commit, a digest of those paths (`setup_digest`) and the plan it started with (`jobs/<id>.plan.yaml`), so the page knows whether the server follows this version (`App.version_view`, `version` in /api/state; for runs from before, git's reflog says which commit was checked out) and what the next run changes. `web/review.py` and `App.review` (`review` in /api/state) compare the saved choices' plan with the last finished run's and with `guests.json`: why a run is due, guests created, deleted, changed and kept, what happens to each disk, the plan sections that differ and every changed line. Its `id` is a digest of the plan, `config.yaml`, the commit and the waiting deletions; the owner's `POST /api/jobs` for a full setup run must name it or gets 409 (`REVIEW_AGAIN`), so setup starts only from Setup, Review and run (`#start-setup`), with what the owner read still true. The agent API, the page agent's `start_job` and stage runs are not held to it. Sessions are kept as SHA-256 of their tokens in `web/sessions.json`, so the restart signs nobody out.
- `src/nullbill/agent.py`: the runtime agent's PVE pool, role and token; `agent_managed` services join the pool and get SSH from the operator (model.py). verify audits the token, then as the agent runs `nb-ssh` to an agent-managed guest (reaches it as `agent`) and to the router (refused), and finds that command in Loki under the uid that ran it; all SKIP until the operator has a credential.
- `src/nullbill/ci.py`: the runner dispatcher's PVE identity. Pool services' golden templates sit in no pool (VM.Clone only); clones go into the `nb-ci` pool at `clone_vmids`, which the dispatcher's token may create, start, stop, set the SMBIOS serial of and destroy. apply bakes each template, so OpenTofu ignores its `template` flag. It records the bake time in the host's textfile collector (`nb_ci_image_baked_timestamp_seconds`) and, once a week old, stops the dispatcher, drains and destroys the clones, `tofu apply -replace`s the template and bakes again (the template's ACLs have `replace_triggered_by` on it, since PVE deletes them with the VM); the page's server runs `apply --stage ci` each Sunday at 03:00, and `CiImageOld` alerts past 14 days.
- `src/nullbill/tofu.py`: OpenTofu JSON for bridges, images and guests (bpg/proxmox); Linux VMs have the guest agent on (the updates role and the CI bake install it), a GPU pinned to `vm:<svc>` goes through a `proxmox_hardware_mapping_pci` (all functions, by slot), Windows VMs use SATA and e1000e (the provider allows one CD-ROM, so no VirtIO ISO); their ISO is `TF_VAR_windows_iso` or else the one ISO on the host whose name holds `win` (`apply.windows_iso`, docs/runbooks/windows-desktop.md); `tools/check-tofu` runs `tofu validate` with the pinned provider in a container and checks that state is encrypted; `tools/render-fixtures` adds a `large-gpu-vm` variant for it.
- `src/nullbill/verify.py`: allowed and denied flows probed from one container per zone and from the LAN, each container's probes side by side in one `pct exec` (`batch`), `PARALLEL` (6) containers at a time, each result printed in order as it comes; SKIP when nothing can run, never PASS. A service whose catalog entry names a `listener` NullBill does not install is DEGRADED, not FAIL, when nothing answers.
- `src/nullbill/pveapi.py`: API calls from inside a guest with the token it holds, and `audit`, which passes only when a token holds exactly the expected privileges. `agent.py` and `ci.py` audit their tokens with it; `forge.py` checks Forgejo (HTTPS, no sign-up, nothing anonymous, TLS to Postgres) from inside its guests.
- `src/nullbill/web/`: the setup page (`server.py`, `static/`): a sidebar of hash-routed pages (Overview, Services, Activity, Alerts; Setup, Access, Agent, Updates under Configure; a tab bar and a More sheet on a phone), a top bar with the one live run (it links to the run's page, `#activity/<id>`), the Setup guide, **Update** when one waits, Run setup (a link to the review; checks and hardware in its menu) and the agent toggle; the agent docked on the right (its own tab on a phone; its head holds a button each for a new conversation, copying it, the log and the settings, and the access mode is three buttons in the message box, nothing behind a menu; suggestions are a list in an empty conversation and wrap above the box after), a command palette (Ctrl+K) and shortcuts (?). Layout that depends on width follows `main`'s container, not the viewport: a laptop with the agent open has a phone's room. Overview lists what needs attention, health from Prometheus, services and recent runs, with the setup guide inline until a setup run has finished (`built` in /api/state; `runs` feeds Activity). Setup is four tabs (hardware, choices, plan, review and run; the agent signs in on the Agent page), and a setup run shows live on the last. Neutral, dense styling: tables and settings rows, status dots, one primary button per place. Owner-facing text names pages, never step numbers. `workloads.py` is Setup, What to run: per choice (a catalog workload, backups, the on-site screen) what it makes, what plan counts for it, what the owner supplies and what turning it off deletes, for the saved choices (`options` in /api/state) and for the unsaved form (`/api/choices/preview`, which writes nothing), so the memory meter and each row follow every tick; a workload apply does not finish (`UNFINISHED`) or the hardware cannot run is shown but cannot be ticked. `services.py` is the Services page: what the owner opens per planned guest, its sign-in, and the only secrets the page reveals (`PASSWORDS`). `progress.py` reads a job's log for the page: apply prints `--- stage <name>, <time>` before each stage (`apply.run_apply`), and a failure becomes the stage, the failed Ansible task or OpenTofu error, and advice from its `ADVICE` table. A running job's **Stop this run** (`/api/jobs/<id>/stop`, `App.stop`) sends SIGTERM, then SIGKILL, to every process under its sh, which records the exit; the job's meta gets `stopped` and the page says so instead of an error. The page is served with a digest of its own files (`server.shell`, in `<meta name="nb-shell">`) and every answer carries the server's (`X-NullBill-Shell`): after **Update NullBill** restarted the server an open page reads another digest and reloads itself, once per digest, or says so while the owner has unsaved choices, a dialog or a draft (an old script cannot read a new server's state; `st.workloads is undefined` was that). The page names `app.js`, `style.css` and `theme.js` with that digest (`?v=`, `server.VERSIONED`), `sw.js` stores a page only with the files it names, and the reload empties the caches first (`reloadFresh`): a phone on a slow line used to get the new page with the old script from the worker's cache. `tools/check` does not open the page in a browser; check page changes with Playwright against `nullbill web` and a stand-in command.
- Page agent (docs/adr/0010-page-agent.md): `src/nullbill/web/chat.py` runs pinned Claude Code headless per turn as `nbagent` (setup-controller makes the user and installs the CLI) with read-only built-in tools plus the MCP server `nullbill agent-tools` (`src/nullbill/agenttools.py`), which calls the page on `/run/nullbill-agent/tools.sock` with a per-turn token. `src/nullbill/web/gate.py` sorts each action into read, change, risky or blocked (lexically: substitutions, `sh -c` and wrappers are read into; variables and unknown programs are at least change; interpreters, scripts and `eval` risky; it is not a sandbox, see the ADR); the owner's mode (Manual, Auto, YOLO, `$NULLBILL_HOME/agent/settings.json`) says which run unasked, the rest become request cards the owner approves (`/api/chat/decide`, risky needs a typed word). Audit in `$NULLBILL_HOME/agent/audit.jsonl` before each action, host commands logged as `nb-cmd` first; output redacted of every secret. A failed run gets one look by the agent (`notice_jobs`). The page is a PWA: `manifest.webmanifest`, `sw.js` (own files only, network first, never `/api/`), icons from `tools/make-icons`; `tests/test_chat.py` drives turns with a fake CLI. `agenttools.TOOLS` must name exactly the `t_*` methods of `chat.Tools`, and its `STAGES` equal apply's (a test checks both). `theme.js` sets a chosen theme before the page draws; without one the CSS follows the system.
- `src/nullbill/artifacts.py`: `apply --dry-run` output, one `build/<machine>/` per target.
- OpenTofu's full apply is of a saved, encrypted plan (`nullbill.tfplan`): `run_tofu` reads it with `tofu show -json` and stops before deleting any guest (VM or container, also when replaced), except a CI image it replaces on purpose, unless the owner confirmed exactly those names (`$NULLBILL_HOME/removals.json`, the page's **Delete and run setup**, `apply --remove-guests`). An unticked workload once took windows-dev's disk with it. After each full apply it records the plan's guests in `$NULLBILL_HOME/guests.json`; the page compares that with the saved choices, shows what the next run would delete (`removals` in /api/state, with `removals_stopped` once a run did stop), and every Run setup then asks first and, on yes, writes those names to `removals.json` itself (`App.confirm_removals`).
- VM host keys: PVE derives cloud-init's instance-id from the VM's cloud-init settings, so a changed NIC (a zone added or gone changes the router's) gave the VM new host keys at its next boot. The updates role's cloud-init drop-in (`ssh_deletekeys: false`, VMs only, never pool images) keeps them; `pin_host_key` re-pins a changed key only from what the VM's guest agent reads inside it (through the host), before each SSH to a VM, once a run.
- `src/nullbill/apply.py`: apply's stages, run in order through a `Reach` (ssh to the host, `ansible-playbook` with a temporary 0600 inventory and vars file). Containers via `community.proxmox.proxmox_pct_remote` with pipelining (`ansible/connection_plugins/nb_pct.py`), VMs as `nullbill` with the host as ProxyJump. A playbook is skipped on a machine that holds the HMAC of the same inputs from its last good run (`src/nullbill/applied.py`, ADR 0005 Reruns); `always=True` for one that depends on time, `--full` or a failed verify runs all. `src/nullbill/secretfile.py`: `$NULLBILL_HOME/secrets.sops.yaml` through sops and age, saved as soon as a secret is made. `tools/check-apply` runs the real Reach against a host container (fake `pct`) and a VM container; `tests/test_apply.py` uses a recording Reach.
- `tools/check`: every check CI runs. Run it before pushing; `tools/check host roles` runs only those parts (`static` is lint, tests and gitleaks) and `ROLES="pbs vpn"` only those role checks (`tools/check-roles pbs vpn` alone). In a TLS-intercepting sandbox set `EXTRA_CA_FILE` to the proxy CA bundle. CI (`.github/workflows/check.yml`) runs the parts as parallel jobs, the role checks in five jobs balanced around inference's llama.cpp build, the three game servers in one (a new role goes into one; `tests/test_ci_skip.py` fails otherwise). A newer push to a PR cancels its running checks.
- Skipping CI: a line `CI-Skip: tofu, firewall` in the PR body leaves out those container checks (`apply install firewall guests host roles tofu`, or `docker` for all); editing the body re-runs CI. Lint, tests, gitleaks and the deny-list hook always run, an unknown name fails the run, and pushes to main run everything except a job a pull request run already passed on the same commit with nothing left out (`tools/ci-passed-on-pr`; main moves only by fast-forward, so that run checked the same tree). Locally, `CI_SKIP=docker tools/check`. Skip only what the diff cannot touch, such as `docker` for a docs-only change.

## Privacy rules (public repo)

- Never commit secrets, real hostnames, IPs, MACs, usernames, emails, serials,
  licence keys or real probe output. Use `example.internal`, RFC 1918 or
  RFC 5737 addresses, placeholder names and synthetic hardware.
- Owner data lives in `$NULLBILL_HOME` outside the repo: `config.yaml`,
  `probe/`, `plan.yaml`, `denylist.txt`, later tofu state and sops files.
- The pre-push hook fails without a non-empty `$NULLBILL_HOME/denylist.txt`.
- When unsure whether something identifies the owner, leave it out and ask.

## Commits and PRs

- Author commits with the owner's GitHub noreply address; no
  `Co-Authored-By`, `Claude-Session` or "Generated with Claude Code" lines.
  `.claude/settings.json` turns that attribution off.
- Commit messages state the change and the reason.
- No stubs committed as done. Unfinished work is an issue. No figures that a
  script in this repo cannot reproduce.

## Working with the owner

- Questions go in `OPEN_QUESTIONS.md`, each with a one-line recommendation.
- Owner approval before anything public, anything that spends money, or any
  tool change (with an ADR draft in `docs/adr/`).
- Nothing touches real hardware without the owner's go for that milestone.
