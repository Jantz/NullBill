# Working inside each service

For the page's agent (and for you at a shell): where each service NullBill
builds lives, what runs it and which command to use instead of guessing.
The agent's `services` tool lists the guests that exist on this server;
`run_command` with `where: <guest>` runs a command as root inside one.

Three things hold in every guest:

- **Look first.** `systemctl --failed`, `systemctl status <unit>`,
  `journalctl -u <unit> -n 50 --no-pager`, `ss -ltnp`.
- **Files under `/etc/nullbill` and anything that says "Generated by
  nullbill" are written by setup** and come back at the next setup run.
  Change what makes them (the choices, `config.yaml`, a setup script), not
  the file.
- **No guest has a route to the internet.** Fetching goes through the
  proxy, which lets only listed names pass. A guest that is off on demand
  must be started first (`on_demand`).

Passwords are on the **Services** page, for the owner. The agent never
reads them and does not need them: each service has a root-side command
below.

## Built-in services

| Guest | Runs as | Listens | Use |
|---|---|---|---|
| `forgejo` | `forgejo.service`, nginx in front | 443 (HTTPS), 22 (its own SSH; the guest has no OpenSSH) | `nb-forgejo ARGS` is Forgejo's own command line as `git`, for example `nb-forgejo admin user list`. Settings: `/etc/forgejo/app.ini` (generated). Data: `/var/lib/forgejo`. |
| `postgres` | PostgreSQL from Debian | 5432, TLS only | `runuser -u postgres -- psql`. Forgejo's database is here. |
| `monitoring` | Prometheus, Alertmanager, Loki, Grafana, `nb-alert-relay.service` | 9090 (Prometheus), 3000 (Grafana through nginx), 3100 (Loki through nginx, client certificate) | Ask Prometheus with the `metrics` tool, not with curl. Alert rules: the role's `nullbill.rules.yml` (generated). `test_alert` sends one to the owner's phone. |
| `step-ca` | `step-ca.service` | 443 | Certificates renew by themselves (`step ca renew --daemon` in each guest). Do not touch its keys. |
| `egress-proxy` | Squid | 3128 | The allow-list is generated from the plan. A name a service of the owner's own needs goes into its `proxy_allow` (`add_service`), never into Squid's file. |
| `jellyfin` | `jellyfin.service` | 8096 | `nb-jellyfin wait`, `nb-jellyfin encoding none` or `qsv DEVICE`, `nb-jellyfin library NAME PATH`, `nb-jellyfin busy`. Kept disks are at `/media/<share>`, read-only. |
| `qbittorrent` | `qbittorrent.service`, `nb-tunnel.service` behind a VPN | 8080 | `nb-torrents space` (room, or why downloads are paused), `nb-torrents tunnel status`, `nb-torrents busy`. Downloads are in `/downloads`, one folder of a kept disk. Folder, room to keep free and the kept disk are `torrents` in the choices (`set_choices`). Which way downloads go (`route`) is the owner's: never choose it for them, and never take, read or print the VPN's WireGuard file (`/etc/nullbill/wg0.conf`), which holds a key; the owner pastes it under **Setup**, **What to run**. Do not change the client's network interface or its routes: `verify` proves them. |
| `files` | Samba | 445 | Shares are generated from the kept disks. `smbstatus` shows who is connected. |
| `inference` | `llama-server.service` | 8080, key required | The model and its options come from the plan (`inference.model`). Logs: `journalctl -u llama-server`. `nvidia-smi` on the Proxmox host shows the GPU. |
| `model-gateway` | `litellm.service`, nginx in front | 4000 (HTTPS) | Offers the local model by name and as `local`. Settings: `/etc/litellm/config.yaml` (generated). |
| `minecraft`, `terraria`, `factorio` | a unit named after the game | the game's one port | Use the page's tools, not a shell: `game_server` (whether it answers, who plays, its log, its worlds), `game_world` (a new world with the game's own options, run a kept one, rename, delete; an upload or download is the owner's, on the Services page) and `game_command` (restart, a line on the console). Never remove or move a world's files by hand: `nb-game world` keeps the list and puts the earlier world back when a change fails. In the guest, `nb-game status`, `nb-game players` and `nb-game admins` answer too. Options are `games.<name>.settings` in the choices (`set_choices`), not the server's files. A Minecraft server's kind (Mojang's own, Paper for plugins, Fabric for mods) and its plugins or mods from Modrinth: `game_mods` (list, search, add, remove, check, update, server), then `start_job` `apply` with stage `games`, which installs the list and restarts the server; never copy a `.jar` into the guest, the role removes what the list does not name. A world Paper has opened opens only under Paper afterwards: before a change to or from Paper, tell the owner what the tool says it costs and have them download the world. A plugin's own settings are files under `/var/lib/minecraft/plugins/<name>/` (Fabric: `/var/lib/minecraft/config/`); there is no tool for them, and many plugins take commands on the console instead (`game_command`). One more server of a game, with its own world and settings: `add_game_server`; its guest has the name the tool answers. |
| `runner-dispatcher` | `nb-dispatcher.service` | 8443 | `journalctl -u nb-dispatcher` says why a CI job did not get a runner. |
| `workspace` | SSH for the owner | 22 | A plain Debian guest for the owner's work and the coding agent. |
| `vpn` | `tailscaled.service` | none | `tailscale status`. Who may reach what is the policy from **Access, People** (`people`, `set_person`), not anything in this guest. Whether devices connect directly or through a relay (**Access, Tailscale, Path**) is measured: `port_mapping` without `enabled` reads it, per device, and `status` carries it as `path_to_the_server`. `port_mapping` with `enabled` only decides whether the server asks the home router for the port or the owner forwards it by hand. It is never a fix for what Path says, and a port forwarded by hand cannot be seen from the server: only a device away from home that answers directly shows it works. |
| `pbs` | `proxmox-backup-proxy.service` | 8007 | Backups run from the Proxmox host each night. Deleting a backup is blocked for the agent in every mode. |
| `router` | nftables, dnsmasq, `nullbill-portmap.timer` | 53 | Everything is generated. A wrong rule is a wrong plan: change the choices and run setup. |

The Proxmox host itself: `pct list`, `qm list`, `pvesh get /nodes/localhost/status`,
`nb-power status` (what is on, off and in use on demand).

## A service of the owner's own

Made with `add_service`; the guest is named after the service
([custom-services.md](custom-services.md)).

- The setup script is at `$NULLBILL_HOME/custom/<name>/setup.sh` on the page's
  side. Inside the guest, `nb-custom-setup` runs it (once per version),
  `nb-custom-setup again` runs it regardless, and its output is in
  `/var/log/nb-custom-setup.log`.
- `check_service <name>` reads all of that at once: whether this version of
  the script ran to its end, failed units, what listens, the log's end.
- A program that listens on `127.0.0.1` only is not reachable from outside
  the guest, whatever the firewall allows. Make it listen on `0.0.0.0`.
- A fix belongs in the script (`add_service` with a new `setup`), so the
  guest can be rebuilt from it. A command run by hand in the guest is gone
  at the next rebuild.

## One job from start to end

For "set up X for me": read [custom-services.md](custom-services.md), then

1. `show_plan` with the steps, so the owner sees where the job is.
2. `add_service` with `build: true`. One card shows the guest, the ports,
   the names it may fetch from and the whole script; the owner types one
   word. That approval saves the service, starts the setup run and starts
   a **task** for the new guest.
3. When the run ends, `check_service`. If something is off, correct the
   script with `add_service`, run `start_job apply stage custom` and check
   again. Inside the task these do not wait for a card each.
4. `finish_task` with what was done, and tell the owner where to open it.

A task never covers the Proxmox host, the NullBill container or the guests
every install has (router, monitoring, step-ca and the like), and a risky
step still waits for the typed word.
